.NET x86 Debugger — Getting started

Debug 32-bit (x86) .NET applications, such as WinForms apps built for x86, in Visual Studio Code — with many of the debugging tools you know from Visual Studio, and a few it doesn't have.

What it is

The C# extension for VS Code ships its debugger only for 64-bit and ARM64, so a process built with <PlatformTarget>x86</PlatformTarget> cannot be debugged with it. This extension bundles a 32-bit build of the open-source debugger netcoredbg and adds the debug type dotnet-x86.

You need

Windows (64-bit), VS Code, a .NET SDK, and the x86 .NET runtime your app uses — for WinForms / WPF that is the .NET Desktop Runtime (x86).

Supported

.NET (Core), .NET 5 or later and .NET Framework 4.x, 32-bit processes: launch and attach. For .NET Framework the x86 .NET runtime (8 or later) is also needed, and the project must write Portable PDBs.

Not supported

.NET Framework 2.0 / 3.5, and Windows PDBs. The debuggee's output goes to the Debug Console (no integrated terminal).

Install

  1. Open the Releases page and download dotnet-x86-debugger-<version>.vsix and install-vsix.ps1 into the same folder.
  2. In that folder, run: 
    powershell -ExecutionPolicy Bypass -File install-vsix.ps1
    Alternatively, in VS Code run Extensions: Install from VSIX... from the Command Palette (Ctrl+Shift+P) and pick the file.
  3. Reload VS Code (Developer: Reload Window).

Menus and messages follow VS Code's display language: English, or Japanese with the Japanese Language Pack.

Your first debug session

1. Make the project 32-bit

<PropertyGroup>
  <OutputType>WinExe</OutputType>
  <TargetFramework>net10.0-windows</TargetFramework>
  <UseWindowsForms>true</UseWindowsForms>
  <PlatformTarget>x86</PlatformTarget>
</PropertyGroup>

2. Add a build task and a launch configuration

.vscode/tasks.json:

{
  "version": "2.0.0",
  "tasks": [{
    "label": "build", "type": "process", "command": "dotnet",
    "args": ["build", "${workspaceFolder}", "-p:Platform=x86"],
    "group": "build", "problemMatcher": "$msCompile"
  }]
}

.vscode/launch.json (type .NET x86 in the Add Configuration... list to insert it):

{
  "version": "0.2.0",
  "configurations": [{
    "name": ".NET x86 Launch",
    "type": "dotnet-x86",
    "request": "launch",
    "preLaunchTask": "build",
    "program": "${workspaceFolder}/bin/x86/Debug/net10.0-windows/MyApp.exe",
    "cwd": "${workspaceFolder}"
  }]
}

3. Set a breakpoint and press F5

Click left of a line number to set a breakpoint (a red dot), then press F5. When the app reaches the line, it stops and VS Code shows the values. Use F10 (step over), F11 (step into), Shift+F11 (step out) and F5 (continue).

If the extension warns that the program will run as a 64-bit process, the project is not built for x86 yet — check PlatformTarget and the path in program (bin/x86/...).

Breakpoints, logpoints and hit counts

Right-click the gutter (left of the line numbers) to add a breakpoint, a conditional breakpoint or a logpoint. To change an existing one, right-click its dot and choose Edit Breakpoint.

KindWhat to typeBehavior
Conditionorder.Amount > 1000Stops only when the expression is true.
Hit count5 or ==5, >=5, >5, %5Stops on the 5th pass / from the 5th / after the 5th / on every 5th pass.
Logpointi={i} total={total} in $FUNCTIONWrites the message to the Debug Console and keeps running. {expression} is evaluated; $FUNCTION and $TID are the method name and thread id.
Use case: a bug appears only around the 300th order of a batch. Set a hit count of >=300 instead of pressing F5 three hundred times, or add a logpoint to print each order's total and look for the first wrong one.

Temporary, dependent, when-changed and caller breakpoints

Right-click a line in a C# editor. These are ordinary breakpoints with a marker in their condition, so they show in the Breakpoints view and can be edited or removed like any other.

CommandCondition it setsBehavior
Add Temporary Breakpoint#onceStops once, then the breakpoint removes itself.
Add Dependent Breakpoint...#after Orders.cs:42Does nothing until the program has stopped at the breakpoint you pick; from then on it stops normally.
Add Breakpoint When Value Changes...#changed order.StatusEvaluates the expression every time the line runs and stops only when the value differs from the previous time. The old and new values are written to the Debug Console.
Add Breakpoint Filtered by Caller...#caller Import.RunStops only when one of the methods is on the call stack (!Import.Run: unless it is). While stopped, the current call stack is offered.

The markers can be typed into any breakpoint's condition and combined with a hit count.

Use case: Save() is called from many places, but the bug only happens after an import. Put a breakpoint in the import, then a dependent breakpoint in Save() on it: you stop only in the saves that follow an import.
Use case: a shared helper such as Save() runs hundreds of times when the screen opens, but the bug is in the import. Instead of a dependent breakpoint you would have to arm first, put #caller Import.Run on the line in Save(): it stops only in the calls the import makes.

Seeing values

  • Hover a variable in the editor to see its value; expand objects in the tooltip.
  • Inline values appear at the end of the lines of the current method (locals, parameters and fields; properties are not evaluated, to avoid running getters). Turn off with the VS Code setting debug.inlineValues.
  • DebuggerDisplay: types with [DebuggerDisplay("Name = {Name}")] are shown with that text everywhere, as in Visual Studio. List<T> shows Count = 3.
  • The Autos view lists the variables of the current and previous line, so you do not have to search the whole Locals tree.
  • Debug.WriteLine / Trace.WriteLine output appears in the Debug Console, with a link to the line that wrote it.

Pinned values

Right-click a line and choose Pin Value to Line... to keep an expression at the end of that line. It is evaluated again in the selected stack frame every time the program stops, so you can watch a value next to the code instead of in the Watch view. Pins are kept with the workspace. Remove them with Unpin Value from Line or .NET x86: Clear All Pinned Values.

Return values

After Step Over or Step Out, the values returned by the methods that were called are shown at the top of the Variables and Autos views — no need to store them in a temporary variable first. A line with several calls shows each of them.

Objects can be expanded; their text is the type name (DebuggerDisplay is not applied to them). The values are shown only at the stop right after the step and disappear on the next step or continue. Calls that end at a breakpoint inside them are not shown, nor are methods returning decimal, DateTime, Nullable<T> or a struct larger than 4 bytes (on x86 these values travel through a hidden buffer).
Use case: if (IsValid(order) && HasStock(order)) takes the wrong branch. Step over it and read which of the two returned false.

Break on value change

Right-click a field, property or local in the Variables view and choose Break on Value Change. Execution stops right after the value changes and the reason shows the old and new value.

How it works and its limits. netcoredbg has no hardware data breakpoints, so the extension finds the lines of your workspace's C# files that assign the name (x = …, x += …, x++), checks the value before and after each of them, and stops only if it changed. Writes through ref / out, from another object (other.x = …) or from code outside the workspace are not detected; the same name is watched for every instance.
Use case: a status field “suddenly” becomes Cancelled and you do not know who sets it. Break on value change takes you straight to the line.

Set next statement

While stopped, right-click a line of the method that is executing and choose Jump to Cursor. The yellow arrow moves there without running the lines in between — run a line again after fixing a value, or skip a call you do not want.

Only lines inside the executing method can be targets, and the runtime refuses moving into or out of a catch / finally block; you then get a message explaining why.

Use case: a calculation went wrong. Change an input with Set Value in the Variables view, jump back to the calculation line, and step over it again — no restart needed.

Step into a specific call

On a line such as Outer(Inner1(), Inner2()), right-click and choose Step Into Target, then pick the call. The other calls run without stopping. The calls are listed in the order they run; if the picked one is not called after all, the step ends on the next line.

Use case: Save(Validate(order), BuildAudit(user)) saves wrong data and you suspect Save. With Step Into you would first walk through Validate and BuildAudit and step out of each; Step Into Target → Save takes you straight there.

Exceptions

  • In the Breakpoints view, tick All Exceptions (when thrown) or User-Unhandled Exceptions. Right-click one and choose Edit Condition to limit it to types: System.NullReferenceException, System.InvalidOperationException, or !System.OperationCanceledException for “all but this”.
  • The Exception Settings view lists common exception types by namespace, as in Visual Studio. Check the types to stop on when thrown; add your own with +, or right-click an Exception Log entry and choose Break When This Type Is Thrown.
  • The Exception Log view lists every thrown exception — type, message, the first line in your code — even when it is caught and ignored, without stopping. Click an entry to open the line. The Debug Console gets Exception thrown: … lines as in Visual Studio.
Use case: a screen shows empty data but no error. The Exception Log reveals a FormatException swallowed by an empty catch.

UI freeze detection

While the program runs, the extension checks a few times a second whether its UI threads still process window messages. When one has not for 2 seconds (dotnetX86.uiFreeze.thresholdMs), the program is paused on that thread: the Call Stack shows the code that holds the UI up, and the pause reads UI not responding for 2.0 s. Stops at breakpoints and steps never count. If the top frames are framework code (e.g. Thread.Sleep, a lock), select your own frame further down. Turn it off with dotnetX86.uiFreeze.enabled.

Use case: the window turns white ("Not Responding") now and then. Just run the app under the debugger; when it happens, you are shown the loop or the blocking call on the UI thread.

Time and performance

PerfTips

After each step or continue, the stopped line shows ≤ 12 ms elapsed. Step over calls one by one to see which is slow.

Section timing

Right-click a line, choose Start Timer Here... and name it; right-click a later line and choose End Timer Here.... Every pass is timed without stopping and charted in the Value Trend view.

Value trend

Right-click a line, choose Track Value at This Line... and enter expressions such as total; items.Count. Each pass records the values without stopping and charts them per expression.

Memory / CPU graph

Run .NET x86: Show Memory / CPU Graph to watch Private Bytes, Working Set and CPU usage once per second. Stopped periods are shaded. Set dotnetX86.memoryGraph.autoOpen to open it with every session.

Use case: memory grows each time a form is opened and closed. Watch Private Bytes while repeating the action; if it never comes down, look for event handlers that are not removed.

Step history

The Step History view keeps the locals of every stop (newest first). Values that changed since the previous stop in the same method are marked changed / new. Click an entry to open its location. It is a history to look at, not a way to run backwards.

Debugging decompiled assemblies

For a DLL without symbols, right-click it in the Modules view and choose Decompile for Debugging.... From the next debug session (a button restarts the current one) you can step into it and set breakpoints in the decompiled C#. The DLL's folder is not touched; Delete Decompiled Symbols removes everything generated.

Use case: a third-party NuGet package throws ArgumentException from deep inside, and the message does not say which value it rejects. Decompile the package, restart, and stop on the throw line: the locals show the value.

Object IDs

Right-click an object in Variables or Watch and choose Make Object ID. The object gets a name, $1, that reaches it from any method and any later stop: in Watch, the Debug Console and breakpoint conditions ($1.Count, order == $2). Values that are that object show {$1}. Like in Visual Studio, the ID does not keep the object alive.

Use case: many carts exist, and one of them gets an item it should not. Make an object ID for the wrong cart when you first see it, then put items == $1 on the line that adds items: you stop only for that cart.

Generate a unit test from a stop

Right-click a frame in the Call Stack view and choose Generate Unit Test from Here. A test that calls the method again with its current arguments (and object) opens beside the editor, in the framework your projects use (xUnit, NUnit or MSTest). Fill in expected and save it in your test project. Stop at the first line of the method to capture the arguments as they came in.

Use case: a customer's order totals wrong. Reproduce it once under the debugger, stop in Total(), generate the test and fill in the right total: the bug is now a failing test, and stays covered after the fix.

Session report

Run .NET x86: Export Debug Session Report (or click the button in the Step History view title) to open a Markdown summary of the last session: program, start / end time and exit code, every stop with the values that changed, the exceptions (with a count per type), section timings, tracked values and the modules with symbols.

Source in another folder

To step into your own library whose PDB records source paths that are not on this machine (e.g. a NuGet package you build elsewhere), add a parent folder of its source to sourceSearchPaths in launch.json (searched with subfolders), or replace a path prefix with sourceFileMap (e.g. { "/_/": "D:\\work\\MyLib\\" }). Both can also be set for every configuration in the settings (dotnetX86.sourceFileMap / dotnetX86.sourceSearchPaths). When a stop has no source here, the Debug Console says which path to map. For a library without symbols, see decompiling.

Use case: your company's shared library comes as a NuGet package built on the CI server. Clone its repository, add the clone to sourceSearchPaths, and step into the library with its real source.

Modules

The Modules view lists the loaded assemblies and whether their symbols (PDB) were found. If a breakpoint stays hollow, check here that your assembly shows symbols loaded.

WinForms controls

While stopped, the WinForms Controls view (collapsed at the bottom of Run and Debug) shows the open forms and their controls as a tree: name, type and text, with hidden controls greyed out. Hover a control for its bounds, enabled state, dock and tab index. Right-click it to Dump Control or Copy Expression; the expression can be pasted into the Watch view.

Use case: a button “does not appear”. The tree tells you whether it exists, which panel it is in, and whether it is hidden or placed outside its parent's bounds.

Click the eye icon (Highlight on Screen) to frame a control on the screen: the form is shown in front, as it was when the program stopped, with a red frame, the control's name and its size for a few seconds.

Use case: the tree says okButton exists and is visible, yet nobody can see it. Highlight it: the frame shows it sitting under another panel, or squeezed to a few pixels at the edge of the form.

Attaching to a running app

Use an attach configuration. The process list shows only x86 .NET processes with their window titles; choose Show all processes... for everything else.

When an app is started by something else (a launcher, a scheduled task) and you need it from the very start, attach by name. Debugging waits until the process appears:

{
  "name": ".NET x86 Attach (wait for process)",
  "type": "dotnet-x86",
  "request": "attach",
  "processName": "OrderApp",
  "waitTimeout": 120
}

Use cases

Legacy x86 dependency

Your WinForms app must stay 32-bit because of an old native DLL or COM component. Debug it in VS Code exactly like a 64-bit app.

“It just shows nothing”

Exception Log finds the exception swallowed by catch { }; click it to open the line.

Wrong value after many items

Track the value at the loop line, look at the chart, then set a hit count to stop right before it goes wrong.

Who changed this?

Break on value change stops at the line that modifies a field.

Is this slow?

Use PerfTips while stepping, then section timing to measure the suspicious part on every pass.

Reproduce a bug in a test

Copy as C# Initializer turns the live data into code for a unit test.

Check loaded data

View as Table shows the List or DataTable as rows; sort, filter, save as CSV.

App launched by another program

Attach with processName and debug it from its first moments.

Which call returned false?

Step over the condition and read the return values in Variables.

Where did my control go?

The WinForms Controls view shows its parent, bounds and visibility.

Write up a bug

Export the session report and attach it: stops, changed values and exceptions in one file.

UI freezes now and then

UI freeze detection pauses the program in the code that holds the UI thread.

Only from this caller

#caller stops a shared method only when a given method called it.

Skip to the call you care about

Step Into Target enters one call of a line and runs the others.

Follow one object

Make Object ID, then use $1 in Watch and conditions anywhere.

Turn a stop into a test

Generate Unit Test from Here writes the method call with the current values.

A library without source

Decompile it from the Modules view and step through the C#.

Library built on another machine

Point sourceSearchPaths at your clone.

Troubleshooting

SymptomWhat to do
“… is a Windows PDB, which this debugger cannot read”Add <DebugType>portable</DebugType> to the .NET Framework project and rebuild.
“Debugging a .NET Framework app needs the x86 .NET runtime”Install the .NET Runtime (x86) 8 or later; the debugger itself uses it.
“… will run as a 64-bit process”Set <PlatformTarget>x86</PlatformTarget> and point program at bin/x86/....
“The x86 dotnet.exe was not found”Install the x86 .NET runtime (for WinForms: .NET Desktop Runtime x86).
Breakpoint stays hollowCheck the Modules view: your assembly needs symbols loaded (Debug build, PDB next to the DLL).
Can’t step into your own library / “Source not found: …” in the Debug ConsoleIts PDB records a path that is not on this machine: add a parent folder of the source to sourceSearchPaths, or map the path prefix with sourceFileMap (and set justMyCode to false for a Release build).
The Variables view is missingIt may have been hidden or moved: run Run and Debug: Focus on Variables View.
Something else is wrongEnable dotnetX86.trace, reproduce, and attach the “.NET x86 Debugger” output to an issue.
