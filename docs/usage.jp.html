.NET x86 Debugger — はじめてのガイド

x86 向けにビルドした WinForms アプリなど、32bit の .NET アプリケーションを Visual Studio Code でデバッグするための拡張機能です。 Visual Studio でおなじみのデバッグ機能の多くに加え、Visual Studio にも無い機能をいくつか備えています。

この拡張機能について

VS Code の C# 拡張に含まれるデバッガは 64bit と ARM64 向けしか配布されていないため、 <PlatformTarget>x86</PlatformTarget> でビルドしたプロセスはデバッグできません。この拡張機能は、オープンソースのデバッガ netcoredbg の 32bit 版を同梱し、デバッグの種類 dotnet-x86 を追加します。

必要なもの

Windows（64bit）、VS Code、.NET SDK、そしてアプリが使う x86 版の .NET ランタイム（WinForms / WPF なら .NET Desktop Runtime (x86)）。

対応

.NET（Core）、.NET 5 以降、.NET Framework 4.x の 32bit プロセス。起動してのデバッグと、実行中のプロセスへのアタッチ。.NET Framework では x86 版 .NET ランタイム（8 以降）も必要で、プロジェクトは Portable PDB を出力する必要があります。

非対応

.NET Framework 2.0 / 3.5、Windows PDB。デバッグ対象の出力はデバッグコンソールに表示されます（統合ターミナルは使えません）。

インストール

  1. Releases ページから dotnet-x86-debugger-<バージョン>.vsix と install-vsix.ps1 を同じフォルダにダウンロードします。
  2. そのフォルダで次を実行します。 
    powershell -ExecutionPolicy Bypass -File install-vsix.ps1
    VS Code のコマンドパレット（Ctrl+Shift+P）で 拡張機能: VSIX からのインストール...（Extensions: Install from VSIX...）を実行し、ファイルを選んでもインストールできます。
  3. VS Code を再読み込みします（Developer: Reload Window）。

メニューやメッセージは VS Code の表示言語に従います。Japanese Language Pack を入れていれば日本語、それ以外は英語で表示されます。

はじめてのデバッグ

1. プロジェクトを 32bit にする

<PropertyGroup>
  <OutputType>WinExe</OutputType>
  <TargetFramework>net10.0-windows</TargetFramework>
  <UseWindowsForms>true</UseWindowsForms>
  <PlatformTarget>x86</PlatformTarget>
</PropertyGroup>

2. ビルドタスクと起動構成を追加する

.vscode/tasks.json:

{
  "version": "2.0.0",
  "tasks": [{
    "label": "build", "type": "process", "command": "dotnet",
    "args": ["build", "${workspaceFolder}", "-p:Platform=x86"],
    "group": "build", "problemMatcher": "$msCompile"
  }]
}

.vscode/launch.json（構成の追加... の一覧で .NET x86 と入力すると挿入できます）:

{
  "version": "0.2.0",
  "configurations": [{
    "name": ".NET x86 Launch",
    "type": "dotnet-x86",
    "request": "launch",
    "preLaunchTask": "build",
    "program": "${workspaceFolder}/bin/x86/Debug/net10.0-windows/MyApp.exe",
    "cwd": "${workspaceFolder}"
  }]
}

3. ブレークポイントを置いて F5 を押す

行番号の左をクリックするとブレークポイント（赤い丸）が置けます。F5 を押してアプリがその行に来ると止まり、VS Code に値が表示されます。 F10（ステップオーバー）、F11（ステップイン）、Shift+F11（ステップアウト）、F5（続行）で進めます。

「64bit プロセスとして起動します」という警告が出たら、プロジェクトがまだ x86 でビルドされていません。 PlatformTarget と、program のパス（bin/x86/...）を確認してください。

ブレークポイント・ログポイント・ヒットカウント

行番号の左を右クリックすると、ブレークポイント、条件付きブレークポイント、ログポイント を追加できます。すでにあるものを変えるには、赤い丸を右クリックして ブレークポイントの編集 を選びます。

種類入力する内容動作
条件order.Amount > 1000式が true のときだけ停止します。
ヒットカウント5 または ==5、>=5、>5、%55 回目で停止 / 5 回目以降 / 5 回目より後 / 5 回ごとに停止。
ログポイントi={i} total={total} in $FUNCTIONメッセージをデバッグコンソールに出して、そのまま実行を続けます。{式} は評価され、$FUNCTION と $TID はメソッド名とスレッド ID に置き換わります。
ユースケース: 一括処理の 300 件目あたりでだけ不具合が出る。F5 を 300 回押す代わりにヒットカウント >=300 を設定するか、ログポイントで各注文の合計を出力して、最初におかしくなる件を探します。

一時・依存・値の変化・呼び出し元のブレークポイント

C# エディターの行を右クリックします。条件欄にマーカーを書いた普通のブレークポイントなので、ブレークポイント ビューに表示され、ほかのブレークポイントと同じように編集・削除できます。

コマンド設定される条件動作
一時ブレークポイントを追加#once1 回停止すると、そのブレークポイントは自動で削除されます。
依存ブレークポイントを追加...#after Orders.cs:42選んだブレークポイントで一度停止するまでは何もしません。それ以降は普通に停止します。
値が変化したときのブレークポイントを追加...#changed order.Statusその行を通るたびに式を評価し、前回と値が異なるときだけ停止します。変化前後の値はデバッグ コンソールに出力されます。
呼び出し元で絞るブレークポイントを追加...#caller Import.Run指定したメソッドがコールスタックにあるときだけ停止します（!Import.Run なら、無いときだけ）。停止中は今のコールスタックが候補に出ます。

マーカーは任意のブレークポイントの条件に直接入力でき、ヒット カウントとも組み合わせられます。

ユースケース: Save() はあちこちから呼ばれるが、不具合はインポートの後だけで起きる。インポート処理にブレークポイントを置き、 Save() にはそれに依存するブレークポイントを置けば、インポートの後の保存でだけ停止します。
ユースケース: 共通処理の Save() は画面を開くだけで何百回も呼ばれるが、不具合はインポート時だけ。先に通過させる必要がある依存ブレークポイントの代わりに、Save() の行へ #caller Import.Run を置けば、インポートからの呼び出しでだけ止まります。

値を見る

  • エディタの変数に マウスを乗せる と値が表示され、オブジェクトはその場で展開できます。
  • インライン値: 現在のメソッドの各行の末尾に値が表示されます（ローカル変数・引数・フィールド。getter の実行を避けるためプロパティは評価しません）。 VS Code の設定 debug.inlineValues で無効にできます。
  • DebuggerDisplay: [DebuggerDisplay("Name = {Name}")] を付けた型は、Visual Studio と同じくその書式で表示されます。 List<T> は Count = 3 と表示されます。
  • 自動変数 ビューには現在の行と直前の行の変数だけが並ぶので、Locals の木を探し回る必要がありません。
  • Debug.WriteLine / Trace.WriteLine の出力は、書き込んだ行へのリンク付きでデバッグ コンソールに表示されます。

値のピン止め

行を右クリックして 値を行にピン止め... を選ぶと、式の値がその行の末尾に表示され続けます。プログラムが停止するたびに、選択中のスタック フレームで評価し直すので、ウォッチ ビューではなくコードの横で値を追えます。ピン止めはワークスペースに保存されます。 行のピン止めを解除 または .NET x86: すべてのピン止めを解除 で外せます。

戻り値の表示

ステップ オーバー や ステップ アウト の後、呼び出したメソッドの戻り値が変数ビューと自動変数ビューの先頭に表示されます。戻り値を確認するためだけに一時変数へ代入する必要はありません。1 行で複数のメソッドを呼んだ場合は、それぞれが表示されます。

オブジェクトは展開できます（表示は型名で、DebuggerDisplay は適用されません）。値はステップ直後の停止でだけ表示され、次のステップか続行で消えます。呼び出し先のブレークポイントで止まった呼び出しと、decimal・DateTime・Nullable<T>・4 バイトより大きい構造体を返すメソッド（x86 では隠しバッファー経由で値を返すため）は表示されません。
ユースケース: if (IsValid(order) && HasStock(order)) が思わぬ分岐に進む。ステップ オーバーして、どちらが false を返したかを読み取ります。

コマンドできることよくある使い方

値が変わったら停止

変数ビューでフィールド・プロパティ・ローカル変数を右クリックし、値の変更時に中断（Break on Value Change）を選びます。値が変わった直後に停止し、停止理由に変化前と変化後の値が表示されます。

仕組みと制限。 netcoredbg にはハードウェアのデータブレークポイントが無いため、この拡張機能はワークスペースの C# ファイルからその名前への代入箇所（x = …、x += …、x++）を探し、各箇所の前後で値を比べて、変わったときだけ停止します。 ref / out 経由の書き換え、別オブジェクトのメンバーへの代入（other.x = …）、ワークスペース外のコードによる書き換えは検出できません。また、同じ名前のメンバーはインスタンスを区別せずに監視します。
ユースケース: 状態を表すフィールドが「いつの間にか」Cancelled になっているが、どこで設定されているのか分からない。値が変わったら停止を使えば、その行で直接止まります。

次のステートメントの設定

停止中に、実行中のメソッドの行を右クリックして カーソルへジャンプ（Jump to Cursor）を選ぶと、間の行を実行せずに黄色い矢印がそこへ移ります。値を直してから行をもう一度実行したり、実行したくない呼び出しを飛ばしたりできます。

移動先にできるのは実行中のメソッド内の行だけで、catch / finally ブロックの内外をまたぐ移動はランタイムが拒否します。その場合は理由を説明するメッセージが出ます。

ユースケース: 計算結果がおかしかった。変数ビューの 値の設定 で入力値を直し、計算の行へジャンプして、もう一度ステップオーバーします。再起動は要りません。

特定の呼び出しへのステップ イン

Outer(Inner1(), Inner2()) のような行で右クリックし、Step Into Target を選んで呼び出しを選びます。ほかの呼び出しは止まらずに実行されます。候補は実行される順に並び、選んだ呼び出しが結局呼ばれなかった場合は次の行で止まります。

ユースケース: Save(Validate(order), BuildAudit(user)) で誤ったデータが保存され、Save が怪しい。ステップ イン だと先に Validate と BuildAudit に入ってはステップ アウトする必要がありますが、Step Into Target → Save なら直接入れます。

例外

  • ブレークポイント ビューで すべての例外（スロー時） または ユーザーコードで未処理の例外 にチェックを入れます。右クリックして 条件の編集 を選ぶと、 型で絞り込めます（例: System.NullReferenceException, System.InvalidOperationException。!System.OperationCanceledException なら「これ以外すべて」）。
  • 例外設定 ビューに、よく使う例外の型が名前空間ごとに並びます（Visual Studio 相当）。スローされたら止めたい型にチェックを付けます。+ で独自の型を追加でき、例外ログの項目を右クリックして この型がスローされたら停止 を選んでも追加できます。
  • 例外ログ ビューには、catch されて無視されたものも含めて すべての スローされた例外が、型・メッセージ・自分のコード内の最初の行とともに、止まらずに並びます。項目を展開すると、スローされた時点のスナップショット（コールスタックと、自分のコードの先頭のフレームのローカル変数）が見られます。 項目をクリックするとその行を開きます。デバッグコンソールにも Visual Studio と同じ Exception thrown: … の行が出ます。
ユースケース: 画面のデータが空なのにエラーが出ない。例外ログを見ると、空の catch で握りつぶされた FormatException が見つかります。

UI フリーズの自動検知

プログラムの実行中、UI スレッドがウィンドウ メッセージを処理しているかを 1 秒に数回確認します。2 秒（dotnetX86.uiFreeze.thresholdMs）処理しないと、そのスレッドでプログラムを一時停止します。コールスタックに UI を止めているコードが表示され、停止理由は「UI が 2.0 秒応答していません」になります。ブレークポイントでの停止やステップ実行はフリーズとみなしません。上のフレームがフレームワークのコード（Thread.Sleep やロック待ちなど）のときは、数フレーム下の自分のコードを選んでください。dotnetX86.uiFreeze.enabled で無効にできます。

ユースケース: ときどきウィンドウが白くなる（応答なし）。デバッガーで実行しておくだけで、起きた瞬間に UI スレッドのループやブロックしている呼び出しが表示されます。

時間とパフォーマンス

PerfTips

ステップ実行や続行のたびに、停止した行に ≤ 12 ms 経過 と表示されます。呼び出しを 1 つずつステップオーバーすれば、どれが遅いかが分かります。

区間の時間計測

行を右クリックして ここから時間を計測... を選んで名前を付け、後の行を右クリックして ここまでの時間を計測... を選びます。通過するたびに止まらずに時間を測り、値の推移 ビューにグラフで表示します。

値の推移

行を右クリックして この行で値の推移を記録... を選び、total; items.Count のように式を入力します。その行を通るたびに止まらずに値を記録し、式ごとにグラフにします。

メモリ / CPU グラフ

コマンドパレットで .NET x86: メモリ / CPU グラフを表示 を実行すると、Private Bytes・Working Set・CPU 使用率を 1 秒ごとに表示します。停止していた区間は網掛けになります。dotnetX86.memoryGraph.autoOpen を有効にすると、デバッグ開始時に自動で開きます。

ユースケース: フォームを開いて閉じるたびにメモリが増える。操作を繰り返しながら Private Bytes を見て、下がらないなら解除し忘れたイベントハンドラを疑います。

ステップ履歴

ステップ履歴 ビューには、停止のたびのローカル変数が新しい順に残ります。同じメソッド内の直前の停止から変わった値には「変化」「新規」と表示されます。項目をクリックするとその位置を開きます。履歴を見返すための機能で、実行を巻き戻すわけではありません。

逆コンパイルしたソースでのデバッグ

シンボルの無い DLL を モジュール ビューで右クリックし、逆コンパイルしてデバッグ可能にする... を選びます。次のデバッグ セッションから（ボタンで今のセッションを再起動できます）、逆コンパイルした C# へのステップ インやブレークポイントが使えます。DLL のフォルダには何も書き込みません。逆コンパイルしたシンボルを削除 で生成物をすべて消せます。

ユースケース: 他社製の NuGet パッケージが奥深くから ArgumentException を投げるが、メッセージからはどの値が悪いのか分からない。パッケージを逆コンパイルして再起動し、throw の行で止めれば、ローカル変数で値が分かります。

オブジェクト ID

変数 ビューか ウォッチ ビューでオブジェクトを右クリックし、オブジェクト ID を作成 を選びます。オブジェクトに $1 という名前が付き、ほかのメソッドや後の停止でも、ウォッチ・デバッグ コンソール・ブレークポイントの条件から参照できます（$1.Count、order == $2）。そのオブジェクトである値には {$1} と表示されます。Visual Studio と同じく、ID はオブジェクトを生かし続けません。

ユースケース: カートが多数あり、そのうち 1 つに入るはずのない商品が入る。最初に見つけたときにそのカートのオブジェクト ID を作り、商品を追加する行に items == $1 を置けば、そのカートのときだけ止まります。

停止時の状態から単体テストを生成

コールスタック ビューでフレームを右クリックし、ここから単体テストを生成 を選びます。そのメソッドを今の引数（とオブジェクト）でもう一度呼ぶテストが、プロジェクトで使っているフレームワーク（xUnit・NUnit・MSTest）で横に開きます。expected を埋めてテスト プロジェクトに保存してください。渡された引数そのものを使いたいときは、メソッドの先頭行で止めます。

ユースケース: ある顧客の注文だけ合計が合わない。デバッガーで一度再現して Total() で止め、テストを生成して正しい合計を書けば、不具合が失敗するテストになり、修正後も回帰を防げます。

セッションの報告書

.NET x86: デバッグ セッションの報告書を出力（またはステップ履歴ビューのタイトルにあるボタン）で、直前のセッションの要約を Markdown で開きます。プログラム・開始/終了時刻・終了コード、各停止と変化した値、例外（型ごとの件数付き）、区間の時間計測、記録した値、シンボルのあるモジュールが含まれます。

ソースが別の場所にある場合

PDB に記録されたソースのパスがこのマシンに無い自作ライブラリ（別の場所でビルドした NuGet パッケージなど）にステップ インするには、launch.json の sourceSearchPaths にソースの親フォルダを追加するか（サブフォルダも探します）、sourceFileMap でパスの接頭辞を置き換えます（例: { "/_/": "D:\\work\\MyLib\\" }）。どちらも設定（dotnetX86.sourceFileMap / dotnetX86.sourceSearchPaths）で全構成に共通にできます。停止位置のソースが無いときは、どのパスを置き換えればよいかをデバッグ コンソールに表示します。シンボルの無いライブラリは 逆コンパイル を使います。

ユースケース: 社内の共通ライブラリが CI サーバーでビルドされた NuGet パッケージとして配られている。リポジトリをクローンして sourceSearchPaths に追加すれば、本物のソースでライブラリにステップ インできます。

モジュール

モジュール ビューには、読み込まれたアセンブリと、シンボル（PDB）が見つかったかどうかが並びます。ブレークポイントが白抜きのままのときは、自分のアセンブリが「シンボル読み込み済み」になっているかをここで確認します。

WinForms コントロール

停止中、WinForms コントロール ビュー（実行とデバッグの下部。初期状態は折りたたみ）に、開いているフォームとそのコントロールがツリーで表示されます。名前・型・テキストを示し、非表示のコントロールは淡色になります。マウスを合わせると、位置とサイズ・有効/無効・Dock・ TabIndex を表示します。右クリックで コントロールをダンプ / 式をコピー。コピーした式はウォッチ ビューに貼り付けられます。

ユースケース: ボタンが「表示されない」。ツリーを見れば、存在するか、どのパネルに入っているか、非表示なのか親の範囲外に置かれているのかが分かります。

コントロールを右クリックして イベントで停止... を選ぶと、そのイベントに登録されたハンドラー（ラムダも含む）の一覧から、次にイベントが発生したときに止まる場所を選べます。どのメソッドがボタンを処理しているか誰も知らない古いコードで役立ちます。

コントロールを右クリックして プロパティを変更... を選ぶと、停止中のプログラムでテキスト・表示/非表示・色・位置・サイズを変えられます。リビルドせずに修正案を試せます。画面には続行すると反映されます。列挙型のプロパティ（Dock、Anchor）は変更できません。

目のアイコン（画面上で強調表示）をクリックすると、コントロールを画面上で枠で示します。停止した時点のフォームが手前に表示され、赤い枠と名前・サイズが数秒間表示されます。

ユースケース: ツリーでは okButton が存在して表示中なのに、誰にも見えない。強調表示すると、別のパネルの下に隠れている、あるいはフォームの端で数ピクセルに縮んでいることが枠で分かります。

実行中のアプリにアタッチする

attach の構成を使います。プロセスの一覧には x86 の .NET プロセスだけがウィンドウタイトル付きで表示されます。それ以外は すべてのプロセスを表示... から選べます。

ランチャーやタスクスケジューラなど、別のものから起動されるアプリを起動直後からデバッグしたいときは、名前でアタッチします。プロセスが現れるまで待ってからアタッチします。

{
  "name": ".NET x86 Attach (wait for process)",
  "type": "dotnet-x86",
  "request": "attach",
  "processName": "OrderApp",
  "waitTimeout": 120
}

ユースケース

古い x86 の依存がある

古いネイティブ DLL や COM コンポーネントのために 32bit のままにしている WinForms アプリを、64bit アプリと同じように VS Code でデバッグできます。

「何も表示されない」

例外ログで、catch { } に握りつぶされた例外が見つかります。クリックでその行へ。

何件目かで値がおかしくなる

ループの行で値の推移を記録してグラフを見てから、おかしくなる直前で止まるようヒットカウントを設定します。

誰がこの値を変えた？

値が変わったら停止を使うと、フィールドを書き換えた行で止まります。

ここは遅い？

ステップ実行中は PerfTips で、怪しい部分は区間の時間計測で毎回測ります。

不具合をテストで再現

C# の初期化子としてコピーで、実際のデータを単体テストのコードにできます。

読み込んだデータの確認

表として表示で List や DataTable を行で確認し、並べ替え・絞り込み・CSV 保存ができます。

別のプログラムから起動される

processName でアタッチすれば、起動直後からデバッグできます。

どの呼び出しが false を返した?

条件の行をステップ オーバーし、変数ビューで戻り値を読みます。

コントロールはどこへ?

WinForms コントロール ビューで親・位置・表示状態が分かります。

不具合をまとめる

セッションの報告書を出力して添付。停止・変化した値・例外が 1 つのファイルに。

ときどき画面が固まる

UI フリーズの自動検知が、UI スレッドを止めているコードで一時停止します。

この呼び出し元のときだけ

#caller で、共通メソッドを特定のメソッドから呼ばれたときだけ止めます。

見たい呼び出しへ直行

Step Into Target で、行の中の 1 つの呼び出しにだけ入ります。

1 つのオブジェクトを追う

オブジェクト ID を作り、$1 をどこでもウォッチや条件に使います。

停止状態をテストに

ここから単体テストを生成で、今の値でメソッドを呼ぶテストを書き出します。

ソースの無いライブラリ

モジュール ビューから逆コンパイルし、C# でステップ実行します。

別のマシンでビルドしたライブラリ

sourceSearchPaths に手元のクローンを指定します。

困ったとき

症状対処
「… は Windows PDB で、このデバッガーでは読み取れません」.NET Framework のプロジェクトに <DebugType>portable</DebugType> を追加して再ビルドします。
「.NET Framework アプリのデバッグには … x86 の .NET ランタイム … が必要」.NET Runtime (x86) 8 以降をインストールします。デバッガー自身が使います。
「64bit プロセスとして起動します」<PlatformTarget>x86</PlatformTarget> を設定し、program を bin/x86/... に向けます。
「x86 版 dotnet.exe が見つかりません」x86 版の .NET ランタイム（WinForms なら .NET Desktop Runtime x86）をインストールします。
ブレークポイントが白抜きのままモジュール ビューで、自分のアセンブリが「シンボル読み込み済み」か確認します（Debug ビルドで、DLL の隣に PDB があること）。
自作ライブラリにステップインできない／デバッグ コンソールに「ソースが見つかりません: …」PDB にこのマシンに無いパスが記録されています。ソースの親フォルダを sourceSearchPaths に追加するか、sourceFileMap でパスの接頭辞を置き換えます（Release ビルドなら justMyCode も false に）。
変数ビューが見当たらない非表示または移動している可能性があります。Run and Debug: Focus on Variables View を実行します。
そのほかの問題dotnetX86.trace を有効にして再現し、出力パネル「.NET x86 Debugger」の内容を添えて Issue を作成してください。
